# Stage 4: Learner model, semantic search, and RAG

**Goal:** Personalize and ground the help. Add a concept taxonomy with original study notes, hybrid retrieval (full-text + vectors, fused, reranked), analogous-problem search, a Bayesian Knowledge Tracing learner model, and similar-past-mistake recall. Measure everything with a labeled retrieval set.

**Prerequisite:** Stage 3 acceptance criteria all pass.

## Standing rules (read first)

1. Read `CLAUDE.md` and `docs/PROGRESS.md` before starting.
2. One task at a time, in order. After each task: run its **Verify** commands, make a conventional commit, tick the box in `docs/PROGRESS.md`.
3. "Decisions already made" are final.
4. Before using a library API you are unsure about (pgvector, sentence-transformers, SQLAlchemy vector types), read its docs or installed types. Do not guess.
5. Ask the user only for: API keys/accounts, manual checks, content review, or uncovered product decisions.
6. After two failed attempts at a task, log it in `docs/BLOCKERS.md` and move on.
7. Never commit secrets, real LeetCode HTML, or copied problem text. All notes must be **original writing**: do not copy or closely paraphrase editorials, blog posts, or books.
8. Out-of-scope ideas go to `docs/BACKLOG.md`.

## Decisions already made

- Embeddings go through an `Embedder` protocol. Default `LiteLLMEmbedder` reads `APORIA_EMBEDDING_MODEL` (the user supplies the provider model string; default dimension constant `EMBED_DIM = 1536`, defined once in `app/rag/constants.py` and used by migrations). `FakeEmbedder` (deterministic hash-seeded vectors with the same dimension) is used in all tests.
- Retrieval = Postgres full-text (`tsvector` + GIN) and pgvector (HNSW, cosine), fused with Reciprocal Rank Fusion (`k = 60`), then an optional cross-encoder rerank (`Reranker` protocol; `NoopReranker` default; `BgeReranker` using `BAAI/bge-reranker-v2-m3` via `sentence-transformers`, installed as the optional uv group `rerank`).
- Learner model: standard BKT update equations implemented by hand in `app/learner/bkt.py` with default priors `p_init=0.2, p_learn=0.15, p_guess=0.2, p_slip=0.1`. Fitting parameters with `pyBKT` is deferred until real data exists (record in `docs/BACKLOG.md`).
- Storage: the learner model and mistake records live **server-side keyed by the anonymous device hash**, and contain only concept ids, short descriptions, and embeddings. They contain **no code**. This differs from the earlier plan to keep learner data local-first, because retrieval needs pgvector. Record this change in `docs/DECISIONS.md` and in `docs/PRIVACY.md` (Stage 6).
- Problem concept summaries are generated by the LLM in its own words (2 to 3 sentences, no statement text, no examples copied) and tagged with 1 to 3 concepts from the taxonomy (structured output, constrained to taxonomy slugs). Only slug, tags, difficulty, and the generated summary are stored; never the full statement.
- Level 4 (worked example): the model invents a **new small problem** that exercises the same concepts and solves it step by step. It must not be the current problem or a trivial renaming of it. The guard checks this.

## Tasks

### 4.1 Schema
Alembic migration `0004_rag_learner`:
- `concepts(slug PK, name, parent_slug null, prerequisites jsonb)`
- `concept_notes(id, concept_slug FK, heading, body, content_hash, embedding vector(EMBED_DIM), tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', heading || ' ' || body)) STORED)` with GIN index on `tsv` and HNSW index on `embedding` (`vector_cosine_ops`).
- `problem_summaries(slug PK FK, summary, concepts jsonb, embedding vector(EMBED_DIM), tsv ...)` with the same indexes.
- `mistakes(id, device_hash, problem_slug, concept_slug, description, embedding vector(EMBED_DIM), resolved bool, created_at)` with an HNSW index and a btree index on `device_hash`.
- `concept_mastery(device_hash, concept_slug, p_known float, n_obs int, updated_at, PRIMARY KEY (device_hash, concept_slug))`.

**Verify:** `uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head`; model tests.

### 4.2 Concept taxonomy
- `knowledge/concepts.yaml`: about 40 concepts with `slug`, `name`, `aliases`, `prerequisites`. Cover: arrays/hashing (hash map lookup, frequency counting, prefix sums), two pointers, sliding window, binary search (on index and on answer), stack, monotonic stack/queue, linked-list manipulation, fast/slow pointers, trees (DFS, BFS, BST properties), heaps/priority queue, graphs (BFS, DFS, topological sort, union-find, shortest path), backtracking, dynamic programming (1D, 2D, knapsack-style, state definition), greedy, intervals, bit manipulation, math/number theory basics, string manipulation, tries, divide and conquer, recursion and base cases, complexity analysis, edge-case reasoning (off-by-one, empty input).
- Loader `app/rag/taxonomy.py` validates the YAML (unique slugs, prerequisites exist, no cycles).

**Verify:** unit tests for the validator including a cycle and a missing prerequisite.

### 4.3 Concept notes (original content)
- Write one note per concept in `knowledge/notes/<slug>.md`, 250 to 400 words each, with this frontmatter and structure:
  ```
  ---
  slug: sliding-window
  concept: sliding-window
  ---
  ## Idea
  ## When it applies
  ## Common mistakes
  ## Socratic questions   (4 to 6 questions that guide without revealing solutions)
  ## Tiny illustration    (an original toy example, not tied to a specific LeetCode problem)
  ## Related concepts
  ```
- Work in batches of 5 concepts; commit after each batch. Keep technical claims precise and conservative; prefer fewer, correct statements over many uncertain ones.
- Add `knowledge/README.md` stating the content is original and must be reviewed by the user.
- **Tell the user** these notes need a human accuracy review before being trusted by the tutor. Add a `reviewed: false` frontmatter field and a script `scripts/mark_reviewed.py` the user can run per file.

**Verify:** a validation script checks frontmatter, section presence, word counts, and that every concept in `concepts.yaml` has a note.

### 4.4 Embeddings and ingestion
- `app/rag/embedder.py` with `Embedder`, `LiteLLMEmbedder` (batch size 64, retries with backoff), `FakeEmbedder`. Cache vectors in Redis by `sha256(model + text)` with a 30-day TTL.
- `app/rag/ingest.py` (`python -m app.rag.ingest`): chunk notes by `##` heading (merge sections under about 80 words with the next section; split above about 400 tokens), compute `content_hash`, and upsert only changed chunks.

**Verify:** unit tests for chunking and for skipping unchanged chunks using `FakeEmbedder`.

### 4.5 Problem summaries and tagging
- Prompt `app/prompts/summarize_problem_v1.md`; structured output `{summary: str, concepts: list[taxonomy slug]}` validated against the taxonomy (reject unknown slugs and retry once).
- Arq job `summarize_problem_job(slug)` triggered the first time a problem is seen; embed and store.

**Verify:** tests with a mocked LLM for valid, invalid-slug-then-retry, and double-invalid (store with empty concepts, mark `needs_review`).

### 4.6 Hybrid retrieval
- `app/rag/retrieve.py`: `fts_search`, `vector_search`, `rrf_fuse(rankings, k=60)` (pure function), `retrieve(query, kind: Literal["notes","problems"], k, mode)` where `mode in {"vector","fts","hybrid","hybrid_rerank"}`.
- Use `websearch_to_tsquery` for full-text queries; filter by `concept_slug` when the caller supplies concepts.
- Reranker: `Reranker` protocol; `BgeReranker` loads lazily; only used when `APORIA_RERANK=1`.

**Verify:** unit tests for `rrf_fuse` (ties, empty lists, one-sided lists); integration tests against Postgres with `FakeEmbedder` for the SQL paths.

### 4.7 Learner model
- `app/learner/bkt.py`: `update(p_known, correct, params) -> float` and `predict_correct(p_known, params)`; pure, tested against hand-computed values.
- `app/learner/service.py`: `record_attempt(device_hash, slug, verdict)`: for each concept of the problem, update `concept_mastery` (treat "Accepted" as correct, other verdicts as incorrect). `record_mistake(device_hash, slug, concept, description)`: store a mistake with an embedding. `weak_concepts(device_hash, k)` returns concepts with the lowest `p_known` among those with `n_obs >= 2`.
- Mistake descriptions are one sentence generated from the failure kind and the minimal failing input (for example "Fails when the array has one element"), with **no code**. Resolve a mistake when the same problem is accepted later.
- Extension sends a `verdict` event for Accepted submissions to `POST /v1/attempts` (body: slug, verdict). Do not send code.

**Verify:** unit tests for BKT math and the service with an in-memory DB session.

### 4.8 Use retrieval and learner data in hints
- Query construction (`app/hints/retrieval_context.py`): concept slugs of the problem + a short natural-language description of the failure (if grounded) + the student's weak concepts overlapping the problem.
- Retrieve up to 3 notes and, for the student, up to 3 similar past mistakes (cosine similarity above a threshold constant). Provide them to the generator as `<notes>` and `<past_mistakes>` blocks with ids.
- Prompts (`hint_l*_v3.md`) tell the model to use notes as background, never to quote them verbatim as an answer, and to mention a past mistake naturally at most once ("last time you had trouble with…").
- Return `sources: [{type: "note", slug, heading}]` in the `done` event; show them as small "Based on" chips in the UI.
- Level 4: retrieve analogous problems (`kind="problems"`) by concept overlap, excluding the current slug. Provide only their summaries; the model writes a fresh worked example.
- Feature flags for evals: headers `X-Aporia-Disable-RAG` and `X-Aporia-Disable-Memory`, honoured only when `APORIA_ENV == "eval"`.

**Verify:** tests with mocked retrieval and LLM: context assembly, citation propagation, flags ignored outside eval.

### 4.9 Retrieval evaluation (`evals/retrieval/`)
- `pairs.csv` columns: `query_id, query, relevant_slugs` (pipe-separated). Draft about 100 queries (student-style descriptions of difficulty such as "my window shrinks too early", plus problem-summary-to-concept queries). Mark every row `needs_human_label` and **ask the user** to review and correct labels; do not report metrics as final until they do.
- `evals/retrieval/run.py`: for each mode (`vector`, `fts`, `hybrid`, `hybrid_rerank`) compute precision@3, precision@5, recall@5, MRR, and latency p50/p95; write `docs/results/retrieval.md` as a table.
- Hint-quality comparison: a promptfoo or Python rubric run on 30 synthetic cases comparing RAG on/off and memory on/off with an LLM-judge rubric (correctness, Socratic-ness, specificity, no leakage), written to `docs/results/hint_quality.md`.

**Verify:** `uv run pytest evals` for metric functions using hand-computed examples (precision@k, MRR). Run the evals only after the user supplies keys and labels.
